Differences from the plan of #714 (both values)
- E5 expected "Read A shows the label and Read B does not". Read A as the PoC takes it is the active configuration, and that did not show the label, so E5 as planned is void: the state it asked for (active configuration holds the label, label resource does not) was not observed. What was observed instead is a different pair: the stored configuration held the label while the active configuration, Read B and Read C did not.
- E1 was to log the mode the node named. The test logs the classified answer: accepted proves NO_REBOOT, and any other mode would show as unrecognised with code OK, which fails the test. It does not print the mode itself, because the apply path is held to one send by guard_test.go and Response carries no mode.
- The label goes into the worker's existing KubeNodeConfig document. A first run appended a second document and stopped on the test's own control; a staged apply of that same text was refused by the node as a duplicate (InvalidArgument, "duplicate document v1alpha1/KubeNodeConfig/ is not allowed").
- Read C was taken for the worker node only (the fixture's control plane is a second node and was not labelled).

Limits
One run, one worker; the poller samples about once a second; E5 is one read 5 s after the staged apply, so it shows the state at that moment and no later one. The fixture shows no reboot, service restart or disk behavior, so nothing here evidences any class other than the label patch. A control-plane node was not applied to. The server cannot take Read B (the Reader reads the active machine configuration only): see ginsys/bronzeward#237.
